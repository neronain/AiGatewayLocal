# PRD v1.6 Addendum
## Access control — รับโครงที่ยืดหยุ่นกว่าจาก LiteLLM มาเท่าที่จำเป็น

**สถานะ:** ร่าง · รอตัดสินใจขอบเขต
**แก้:** PRD §7 (Identity, permission and access) · §8 (Quota) · §12 (Data model)
**ไม่แก้:** §4 capability registry · §9 routing · §14 model test suite

### 0. ทำไมต้องมีเอกสารนี้

เจ้าของระบบดู Access Control ของ LiteLLM แล้วเห็นว่า**แยกย่อยได้มากกว่าและครอบคลุม
กว่าของเรา** จึงอยากได้โครงแบบนั้นมา

เอกสารนี้จึงเริ่มจากการ**วัดว่า LiteLLM มีอะไรจริง ๆ** ด้วยการยิง API ของมันที่รันอยู่
(v1.96.2 · `sk-spike-test-key` บน Autodeploy VM) ไม่ใช่จากหน้าจอหรือเอกสาร แล้วค่อย
เทียบกับของเราทีละข้อ

### 1. LiteLLM มีอะไร (วัดจาก API ของมันเอง)

#### 1.1 ลำดับชั้นสี่ระดับ

```
Organization ──< Team ──< Internal User ──< Key
```

ทุกชั้นถือค่าชุดเดียวกันได้: `models` · `max_budget` · `budget_duration` ·
`tpm_limit` · `rpm_limit` · `max_parallel_requests` · `blocked` · `metadata`
key ที่ออกภายใต้ team ถูกจำกัดด้วยเพดานของ team และ org เหนือขึ้นไป

**93 ฟิลด์บนหนึ่ง key** ในนั้นมีค่าที่สืบมาจากชั้นบนติดมาด้วย เช่น `team_max_budget`,
`organization_tpm_limit`, `team_member_spend` — คือ key ตัวเดียวรู้เพดานของทุกชั้น

#### 1.2 Access Group — มัดทรัพยากรตั้งชื่อไว้ แล้วแจกทั้งมัด

`AccessGroupResponse` ที่ API คืนมาจริง:

| ฟิลด์ | คืออะไร |
|---|---|
| `access_group_name` · `description` | ชื่อมัด |
| `access_model_names` | โมเดลในมัด |
| `access_mcp_server_ids` | MCP server ในมัด |
| `access_agent_ids` | agent ในมัด |
| `assigned_key_ids` · `assigned_team_ids` | ใครได้มัดนี้ไปบ้าง |

จุดสำคัญคือ**ตั้งชื่อครั้งเดียว แจกได้หลายที่** ไม่ต้องไปไล่ติ๊กโมเดลใหม่ทุก key ทุก team

#### 1.3 Budget เป็นวัตถุที่ใช้ซ้ำได้

`BudgetNewRequest`: `budget_id` · `max_budget` · `soft_budget` · `budget_duration` ·
`tpm_limit` · `rpm_limit` · `max_parallel_requests` · `model_max_budget`

สร้างงบไว้ก้อนหนึ่งแล้วผูกให้ key/team/user หลายตัวใช้ร่วมกัน · `model_max_budget`
คืองบรายโมเดลในก้อนเดียวกัน

#### 1.4 ค่าเริ่มต้นของสมาชิกใน team

`default_team_member_models` · `team_member_budget` · `team_member_rpm_limit` ·
`team_member_key_duration` · `team_member_permissions`

แปลว่า "ใครเข้ามาในทีมนี้ key ที่ออกให้เขาเริ่มต้นแบบนี้" — ตั้งครั้งเดียวใช้กับทุกคน

#### 1.5 อื่น ๆ ที่มี

- `blocked` บน team และ key — ระงับชั่วคราวโดยไม่ลบ
- เจ้าของ key แยกชนิด: You / Service Account / Another User / Agent
- `allowed_routes`, `permissions` ต่อ key
- `auto_rotate`, `rotation_interval` — หมุน key อัตโนมัติ

### 2. ของเรามีอะไร (วัดจากโค้ด)

```
User ──< Membership >── Workspace ──< WorkspaceModel
 │                          │
 └────< ApiKey >────────────┘        ApiKey.workspace_id · ApiKey.models
```

| ความสามารถ | ของเรา | ที่ไหน |
|---|---|---|
| จำกัดโมเดลตามกลุ่ม | ✅ | `WorkspaceModel` |
| จำกัดโมเดลต่อ key | ✅ | `ApiKey.models` (v1.5) |
| สืบสิทธิ์จากกลุ่มของเจ้าของ | ✅ | `permitted_aliases()` (v1.5) |
| ขอบเขตของ manager | ✅ | `managed_workspaces()` (v1.5) |
| โควตาตามช่วงเวลา | ✅ | `QuotaPolicy` · day/month/term · requests/tokens/images |
| โควตาแยกรายโมเดล | ✅ | `QuotaPolicy.model_alias` |
| ลำดับความสำคัญของโควตา | ✅ | user+model > user > workspace+model > workspace > global |
| หมดอายุ key | ✅ | `ApiKey.expires_at` |
| เพิกถอน key | ✅ | `revoked_at` |

**ที่ยังไม่มี** เทียบกับ LiteLLM:

| ขาด | ผลจริงกับผู้ใช้ |
|---|---|
| ชั้น Organization เหนือ workspace | มหาลัยที่มีหลายคณะต้องตั้ง workspace แบน ๆ ปนกัน แยกงบต่อคณะไม่ได้ |
| มัดโมเดลตั้งชื่อ (Access Group) | เปิดโมเดลชุดเดิมให้ 20 วิชา = ไล่ติ๊ก 20 รอบ · เพิ่มโมเดลใหม่ = ไล่แก้ 20 รอบ |
| งบเป็นวัตถุใช้ซ้ำ | ตั้งโควตาเหมือนกัน 20 ชุดแทนที่จะผูกก้อนเดียว |
| ลิมิตต่อนาที (tpm/rpm) | โควตารายวันกันการใช้เกินระยะยาวได้ แต่กัน burst ไม่ได้ · ตอนนี้พึ่ง nginx ต่อ IP ซึ่งไม่ใช่ต่อคน |
| งานพร้อมกันต่อ key | นักศึกษาคนเดียวเปิด 10 แท็บกิน slot ของทั้งห้องได้ |
| ค่าเริ่มต้นของสมาชิกกลุ่ม | ออก key ให้ 30 คนต้องตั้งค่าเดิมซ้ำ 30 รอบ |
| ระงับทั้งกลุ่มชั่วคราว | ต้องไล่เพิกถอน key ทีละใบ ซึ่งย้อนกลับไม่ได้ |
| key ของระบบ vs ของคน | key ของ CI กับของนักศึกษาหน้าตาเหมือนกัน ตอนไล่ตรวจแยกไม่ออก |

### 3. ข้อเสนอ — รับอะไร ไม่รับอะไร

หลักที่ใช้ตัดสิน: **รับสิ่งที่แก้ปัญหาที่นับได้ในบริบทมหาลัย/บริษัท ไม่รับสิ่งที่มีไว้
เพราะ LiteLLM ขาย SaaS หลาย tenant**

#### รับ · P0

**FR-60 · Access Group — มัดโมเดลตั้งชื่อไว้**

ตารางใหม่ `AccessGroup(id, name, description, models[])` ผูกกับ workspace และ key ได้
`permitted_aliases()` ขยายมัดออกเป็นรายชื่อโมเดลตอนคิดสิทธิ์

เหตุผล: เป็นข้อที่คุ้มที่สุดต่อความพยายาม · การเปิดโมเดลใหม่ให้ทั้งคณะควรเป็นการแก้
ที่เดียว ไม่ใช่ยี่สิบที่ · และมันแก้ปัญหาที่จะโตขึ้นเรื่อย ๆ ตามจำนวนวิชา

**FR-61 · ลิมิตต่อนาทีและงานพร้อมกันต่อ key**

เพิ่ม `rpm_limit`, `tpm_limit`, `max_parallel_requests` เข้า `QuotaPolicy`
(ไม่สร้างตารางใหม่ — โครง scope/precedence ที่มีอยู่รองรับได้เลย)

เหตุผล: โควตารายวันไม่กัน burst · ห้องเรียน 40 คนกดพร้อมกันตอนต้นคาบทำให้เครื่อง
คิวยาวจนคนที่มาทีหลังรอเป็นนาที ซึ่งเป็นสถานการณ์จริงของการใช้ในห้องเรียน

**FR-62 · ระงับกลุ่มชั่วคราวโดยไม่ลบ** · *ทำแล้ว 2026-08-14*

`PATCH /admin/workspaces/{id}/status` รับ `active` | `suspended` · วิชาที่ถูกระงับ
ไม่ให้โมเดลอะไรเลย ต่างจากการเพิกถอน key ตรงที่**ย้อนกลับได้**

**ไม่ต้องเพิ่มคอลัมน์** — `Workspace.status` มีมาตั้งแต่รุ่นแรกและไม่มีอะไรอ่านมันเลย
รูปแบบเดียวกับ `Membership` ก่อน v1.5 คือฟิลด์ที่หน้าตาเหมือนสวิตช์แต่ไม่ได้ต่อกับอะไร

**ไม่รับ `blocked` บน key** ตามที่ LiteLLM มี — `User.status` บังคับใช้อยู่แล้วสำหรับ
ระงับรายคน และการมีสวิตช์ปิดอันที่สามข้าง `revoked_at` กับ `expires_at` คือความเสี่ยง
ที่ §5 เตือนไว้เอง

> **บั๊กที่เทสจับได้ระหว่างทำ** ครั้งแรกผมกรอง `Workspace.status` ที่ฝั่ง membership
> ผลคือวิชาที่ถูกระงับกลายเป็น "คนนี้ไม่อยู่กลุ่มไหนเลย" ซึ่งคือกรณี*ไม่จำกัด* —
> ระงับวิชาแล้วนักศึกษาได้ทั้งแคตตาล็อกแทนที่จะไม่ได้อะไร · ต้องกรองที่ฝั่ง*โมเดล*
> เท่านั้น membership ต้องยังนับว่ามีอยู่

#### รับ · P1

**FR-63 · ค่าเริ่มต้นของสมาชิกในกลุ่ม**

`Workspace.default_member_models[]` และ `default_key_days` — ออก key ให้สมาชิกแล้ว
ได้ค่านี้เป็นค่าตั้งต้น (แก้รายคนได้)

**FR-64 · ชนิดเจ้าของ key**

`ApiKey.kind` = `person` | `service` · ใช้แค่เพื่อการมองเห็นและการกรอง ไม่เปลี่ยนกติกา
สิทธิ์ — key ของ CI ที่ปนอยู่กับ key นักศึกษาคือสิ่งที่ทำให้ audit ยาก

#### ไม่รับ

| ไม่รับ | เพราะ |
|---|---|
| ชั้น Organization | ยังไม่มีใครขอ · เพิ่มชั้นที่ไม่มีคนใช้คือเพิ่มความงงให้ทุกคน — ปัญหาเดิมที่ทำให้ต้องเขียน v1.4 · เก็บไว้จนกว่าจะมีมหาลัยที่ต้องแยกคณะจริง |
| Budget เป็นวัตถุใช้ซ้ำ (`budget_id`) | `QuotaPolicy` ที่ผูกกับ scope ให้ผลเดียวกันโดยไม่ต้องจัดการวงจรชีวิตของวัตถุอีกชนิด · ถ้าอยากใช้ซ้ำ ให้ตั้งที่ระดับ workspace ซึ่งใช้ร่วมกันอยู่แล้ว |
| งบเป็นเงิน (`max_budget` USD) | โมเดลรันบนเครื่องตัวเอง ไม่มีค่า token · ตัวเลขเงินที่ไม่มีเงินจริงอยู่เบื้องหลังคือตัวเลขหลอก |
| `auto_rotate` / `rotation_interval` | หมุน key อัตโนมัติโดยไม่มีทางส่งใบใหม่ถึงมือผู้ใช้ = ทำให้ของพังตามกำหนดเวลา |
| `allowed_routes` ต่อ key | เรามี `scopes` อยู่แล้วและยังไม่มีใครใช้จนเต็ม |
| Agent / MCP ใน access group | ยังไม่มีสองอย่างนี้ในระบบ · ออกแบบเผื่อของที่ยังไม่มีคือการเดา |

### 5. ความเสี่ยง

| ความเสี่ยง | ผล | กัน |
|---|---|---|
| เพิ่มชั้นแล้วคนงงกว่าเดิม | ปัญหาเดียวกับที่ทำให้ต้องเขียน v1.4 | ไม่เพิ่มชั้นใหม่ (ไม่รับ Organization) · access group เป็น *ทางลัด* ของสิ่งที่ทำได้อยู่แล้ว ไม่ใช่กติกาใหม่ |
| access group ทำให้สิทธิ์กว้างขึ้นโดยไม่ตั้งใจ | คนได้โมเดลที่ไม่ควรได้ | มัดต้องขยายเป็นรายชื่อแล้ว **intersect** กับกติกาเดิมเสมอ · จำกัดได้อย่างเดียว ขยายไม่ได้ เหมือนกฎที่มีอยู่ |
| rpm/tpm ตั้งต่ำไปแล้วห้องเรียนพัง | ผู้ใช้โดนปฏิเสธกลางคาบ | default = ไม่จำกัด · ต้องตั้งเองเท่านั้น · error บอกชัดว่าโดนลิมิตไหนและรออีกนานเท่าไร |
| `blocked` สับสนกับ `revoked` | เข้าใจผิดว่ากู้คืนได้/ไม่ได้ | คำในหน้าเว็บต้องต่างกันชัด: "ระงับชั่วคราว" กับ "เพิกถอนถาวร" |

### 6. คำถามสามข้อ และคำตอบ

ทั้งสามข้อตอบได้จากหลักการที่ระบบยึดอยู่แล้ว ไม่ต้องตั้งกติกาใหม่

**1. access group ผูกกับอะไรได้บ้าง → ทั้ง workspace และ key**

ยืดหยุ่นกว่าและไม่เพิ่มความเสี่ยง เพราะมัดถูกขยายเป็นรายชื่อแล้ว **intersect** กับสิ่งที่
คนนั้นมีสิทธิ์อยู่แล้วเสมอ — เป็นทางลัดในการ*เขียน*กติกา ไม่ใช่ทางใหม่ที่ทำให้สิทธิ์กว้างขึ้น
กฎเดิม "จำกัดได้อย่างเดียว ขยายไม่ได้" ยังคุมอยู่ทั้งหมด

**2. rpm/tpm นับที่ระดับไหน → ต่อคน (`user_id`)**

ตรงกับเจตนา: เปิดสิบแท็บก็ยังเป็นคนเดียว และตรงกับ `QuotaPolicy` ที่นับต่อคนอยู่แล้ว
การนับต่อ key จะทำให้คนที่ออก key เพิ่มได้สิทธิ์เพิ่มฟรี ซึ่งเป็นช่องที่ไม่ควรมี

**3. ระงับ workspace แล้ว key ที่ผูกอยู่เป็นอย่างไร → กลุ่มนั้นเลิกให้สิทธิ์**

ไม่เพิ่มกติกาใหม่ · กลุ่มที่ถูกระงับ = กลุ่มที่ไม่ให้โมเดลอะไรเลย ผลจึงไหลตามกฎเดิม:
คนที่อยู่กลุ่มอื่นด้วยยังใช้ของกลุ่มนั้นได้ · key ที่ผูกกับกลุ่มที่ถูกระงับใช้อะไรไม่ได้เลย
ซึ่งตรงกับความหมายของ "ระงับวิชานี้ไว้ก่อน"
