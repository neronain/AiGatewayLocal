# PRD v1.5 Addendum
## Models & Endpoints — รับโครงของ LiteLLM มาโดยไม่ทิ้งสิ่งที่เรามีดีกว่า

**สถานะ:** ร่าง · ยังไม่อนุมัติ
**แก้:** PRD §4 (Capability registry) · §10 (Member-facing model UX)
**อ้างอิง:** วัดจาก LiteLLM ที่รันจริงบน backend ของเราเอง 2026-08-14 (ไม่ใช่จากเอกสาร)

---

### 0. โจทย์

> "ส่วนของ gateway ตอนที่จัดการ manage model ผมอยากให้ออกแบบการทำงานแบบในส่วน
> Models + Endpoints ของ litellm ทั้งหมด"

เอกสารนี้แยกว่าอะไรใน LiteLLM ที่ควรรับมา อะไรที่เรามีอยู่แล้ว และอะไรที่**ไม่ควร
รับมาเพราะของเราถูกต้องกว่า** — ข้อสุดท้ายสำคัญที่สุด

---

### 1. สิ่งที่วัดได้จาก LiteLLM ที่รันจริง

**โครงข้อมูลของมัน**

```
model_name  ────< deployment
(สิ่งที่ client เรียก)   litellm_params: api_base, api_key, model, tpm, rpm
                        model_info:     id, db_model, access_via_team_ids
```

หลาย deployment ที่ใช้ `model_name` เดียวกัน = **model group** → กระจายโหลด/สำรอง

**API ที่มี** (`/model/new` `/model/update` `PATCH /model/{id}/update` `/model/delete`
`/model/block` `/model/unblock` `/model/info` `/model_group/info` `/health/test_connection`
`/team/model/add` `/team/model/delete` `/public/model_hub`)

**และจุดที่มันแพ้ของเราอย่างชัดเจน**

`/model_group/info` รายงาน `muse` ว่า:

```
supports_vision            false
supports_function_calling  false
supports_reasoning         false
```

ซึ่ง **ผิดทั้งสามข้อ** — เราทดสอบกับ backend ตัวเดียวกันแล้วได้ vision ถูก (ตอบ
`red` จาก PNG 224×224), tool_use + tool_result ครบ, และมี `thinking` block จริง

สาเหตุ: LiteLLM อ่านความสามารถจาก **แผนที่ค่าคงที่ในตัวมัน** โดยเทียบจากชื่อโมเดล
โมเดลที่เรา self-host ไม่มีในแผนที่นั้น ทุกอย่างจึงเป็น `false` (มี warning
`not in built-in cost map` ตอน startup)

ของเราประกาศความสามารถต่อโมเดล **แล้วพิสูจน์ด้วย MODEL-001..010 ที่ยิงใส่ backend
จริง** — สำหรับระบบที่รันโมเดลบนเครื่องตัวเอง นี่ไม่ใช่แค่ต่างกัน แต่ถูกกว่า

### 2. เทียบกับของที่เรามีอยู่

| ความสามารถ | LiteLLM | LiteGate วันนี้ |
|---|---|---|
| alias เดียวหลาย backend | model group | **มีแล้ว** (`coding` 2 · `coder-next` 2) |
| เพิ่ม/แก้/ลบ จากหน้าเว็บ | มี | **มีแล้ว** (`/admin/models` POST/DELETE, Edit) |
| สุขภาพราย endpoint | มี | **มีแล้ว** (2/2 up) |
| ความสามารถของโมเดล | แผนที่ค่าคงที่ · **ผิดกับ local** | **ประกาศ + ทดสอบจริง** |
| ชุดทดสอบยิง backend | ไม่มี | **MODEL-001..010** |
| ทดสอบการต่อ**ก่อน**บันทึก | `/health/test_connection` | **ไม่มี** |
| ปิดโมเดลชั่วคราวโดยไม่ลบ | `/model/block` | **ไม่มี** |
| ลิมิต tpm/rpm ต่อ endpoint | มี | ไม่มี (มี quota ต่อคนแทน) |
| หน้ารวมโมเดลสาธารณะ | `/public/model_hub` | ไม่มี |
| แยก "กลุ่ม" กับ "deployment" ใน UI | ชัด | ปนกันในตารางเดียว |

**ข้อสรุป: โครงของเราเป็นแบบเดียวกับ LiteLLM อยู่แล้ว** ที่ขาดคือสี่อย่างท้ายตาราง
ไม่ใช่ต้องรื้อทั้งส่วน

### 3. ข้อกำหนด

#### FR-50 — ทดสอบการต่อก่อนบันทึก · **P0** *(มีอยู่แล้ว · ยืนยัน 2026-08-14)*

ก่อนเพิ่ม/แก้ endpoint ต้องกดทดสอบได้ว่าต่อถึงจริง เสิร์ฟโมเดลชื่ออะไร ตอบ chat ได้ไหม
**โดยยังไม่เขียนลง registry**

เหตุผลจากของจริง: session นี้เสียเวลาหลายรอบกับ endpoint ที่ config ถูกแต่ปลายทาง
ไม่ใช่อย่างที่คิด (bifrost ตอบ 405 กับ `/v1/messages`, dgx-direct ประกาศ
`anthropic: false` ทั้งที่ตอบได้) ทดสอบก่อนบันทึกจับได้ทั้งสองเคส

**ไม่ต้องสร้าง `POST /admin/models/test-connection` ใหม่** — `POST /admin/models/detect`
ทำงานนี้อยู่แล้ว และปุ่ม **Detect** อยู่ในทุกแถว backend ทั้งตอนเพิ่มและตอนแก้ ยิงกับ
เครื่องจริงยืนยันแล้วว่าจับสองเคสในย่อหน้าบนได้ตรง:

| backend | ประกาศไว้ | ที่วัดได้ |
|---|---|---|
| dgx-direct `:8000` | `anthropic: true` | `anthropic: true` · เสิร์ฟ `Qwen3-Coder-30B-A3B-Instruct` · ctx 262,144 |
| dgx-bifrost `:8081` | `anthropic: false` | `anthropic: false` · เสิร์ฟ 2 โมเดล · ctx อ่านไม่ได้ ต้องกรอกเอง |

ข้อจำกัดที่รู้ตัว: กด **Save to registry** คือเขียนไฟล์ใหม่ทั้งไฟล์ คอมเมนต์ในไฟล์หาย
(ต่างจากปุ่มเปิด/ปิดใน FR-51 ที่แก้บรรทัดเดียว) ตอนนี้เขียนเตือนไว้ใต้ปุ่ม ยังไม่แก้ให้
รักษาคอมเมนต์ในเส้นทางบันทึกทั้งก้อน เพราะต้องเอา object ที่ผ่าน validate แล้ว merge
กลับเข้า tree เดิม ซึ่งเสี่ยงกว่าประโยชน์ที่ได้

#### FR-51 — ปิดโมเดลชั่วคราวโดยไม่ลบ · **P0** *(ทำแล้ว 2026-08-14)*

`enabled: false` มีอยู่ในสคีมาแล้วแต่หน้าเว็บไม่มีปุ่ม · ตอนนี้ทางเดียวคือลบไฟล์ทิ้ง
แล้วสร้างใหม่ ซึ่งทำให้ config ที่ปรับมาแล้วหายไปทั้งหมด

`PATCH /admin/models/{alias}/enabled` — ส่ง `{"enabled": false}` เพื่อปิดทั้ง alias
หรือใส่ `"endpoint": "<ชื่อ>"` เพื่อปิดเครื่องเดียวโดยที่ alias ยังรับงานจากเครื่องที่เหลือ
ในหน้าเว็บคือปุ่ม Disable/Enable ท้ายแถว กับลิงก์ "ปิดเครื่องนี้" ใต้ backend แต่ละตัว

สองอย่างที่พบตอนทดสอบบนเครื่องจริง แล้วแก้ไปด้วย:

* **เขียนไฟล์ใหม่ทั้งไฟล์กินคอมเมนต์** — `write_model` สร้างเอกสารใหม่จาก object ที่
  parse มาแล้ว คอมเมนต์จึงหายหมด · รับได้ตอน admin กดบันทึกจากฟอร์ม แต่รับไม่ได้ตอน
  กดสวิตช์ · การกดครั้งแรกบนเครื่องจริงกินคอมเมนต์ 6 บรรทัดที่อธิบายว่าทำไม
  spark-worker ตั้ง 1 slot · ตอนนี้ `set_enabled_in_file()` แก้เฉพาะบรรทัดนั้นบรรทัด
  เดียว ถ้าหาไม่เจอค่อยถอยไปเขียนใหม่ทั้งไฟล์แบบเดิม
* **ช่อง Health นับเครื่องที่ปิดไว้ว่ายังรับงาน** — ปิดไปหนึ่งเครื่องแต่ยังขึ้น `2/2 up`
  ตอนนี้นับเฉพาะเครื่องที่เปิดอยู่ และบอก "ปิดไว้ N" แยกต่างหาก เพราะ *ปิดเอง* กับ *ล่ม*
  เป็นคนละเรื่อง

กติกา "อย่างน้อยหนึ่ง endpoint ต้องเปิด" ไม่ได้เขียนซ้ำที่ API — สคีมาบังคับอยู่แล้ว
(`ModelSpec`) เส้นทางนี้แค่ตรวจซ้ำผ่าน `validate_definition()` ก่อนเขียน ไม่งั้นไฟล์ที่
loader จะปฏิเสธจะถูกเขียนลงไปก่อน แล้วค่อยไปพังตอน reload

#### FR-52 — แยกมุมมอง "alias" กับ "endpoint" ให้ชัด · **P1** *(ทำแล้ว 2026-08-14)*

แถวบนคือสิ่งที่ client เรียก (alias, ความสามารถ, context) · แถวย่อยคือเครื่องจริงที่
รองรับมัน (host, engine, สุขภาพ, priority) — ตอนนี้ปนกันในเซลล์เดียว อ่านยากเมื่อ
alias มีหลาย endpoint

ตารางเป็นสองชั้นแล้ว · แถว `alias-row` ตามด้วยแถว `ep-row` ของเครื่องที่รับงานให้ alias
นั้น เยื้องเข้าไปและพื้นหลังจมลง เส้นคั่นอยู่ที่ท้ายกลุ่ม ไม่ใช่ระหว่างแถว — ไม่งั้นสาม
backend จะอ่านเหมือนสามโมเดลที่ไม่เกี่ยวกัน

แถวเครื่องบอกสิ่งที่เป็นของเครื่องล้วน ๆ: ที่อยู่ · โปรโตคอลที่ *เครื่องนั้น* พูดได้ ·
สุขภาพของตัวเอง · priority กับจำนวนงานพร้อมกัน (และงานที่กำลังวิ่งถ้ามี) · ปุ่มปิด/เปิด
ส่วนแถว alias เหลือเฉพาะสิ่งที่เป็นของ alias: ความสามารถที่ประกาศ ผลวัด และปุ่มที่
กระทำกับทั้งโมเดล

#### FR-53 — ความสามารถต้องมาจากการวัด ไม่ใช่จากชื่อ · **P0** *(คงไว้ ไม่เปลี่ยน)*

ห้ามรับวิธีของ LiteLLM มาใช้ · ความสามารถที่ประกาศต้องมี "ตรวจครั้งล่าสุดเมื่อไร ผลอะไร"
กำกับ และหน้าเว็บต้องแยกให้เห็นระหว่าง *ประกาศไว้* กับ *ทดสอบแล้ว*

เคสจริงที่ทำให้ข้อนี้จำเป็น: `general` ประกาศ `anthropic: false` แต่ backend ตอบได้ ·
`coding` ประกาศ context 65,536 แต่ของจริง 262,144 — สองเคสนี้ถูกจับได้เพราะวัด ไม่ใช่
เพราะอ่านชื่อ

#### FR-54 — ลิมิตต่อ endpoint · **P2**

`max_concurrency` มีแล้ว · tpm/rpm ยังไม่มี ยกไว้จนกว่าจะมีเครื่องที่ต้องใช้จริง

#### NFR-50 — registry ยังเป็นไฟล์ YAML · **P0**

LiteLLM เก็บโมเดลใน database · ของเราอยู่ใน `config/models/*.yaml` ซึ่งอ่านได้ด้วยตา
เทียบ diff ได้ ใส่ git ได้ และ `scripts/backup.sh` เก็บไปด้วยแล้ว — **ไม่ย้ายลง
database** การแก้จากหน้าเว็บต้องเขียนกลับเป็น YAML เหมือนเดิม

### 5. สิ่งที่ **ไม่** รับมาจาก LiteLLM

- **แผนที่ความสามารถค่าคงที่** — ผิดกับโมเดล self-host ทุกตัว (ดู §1)
- **เก็บ registry ใน database** — YAML อ่าน/diff/backup ได้ดีกว่าสำหรับระบบที่แจกต่อ
- **ราคาต่อ token / spend tracking** — โมเดลรันบนเครื่องตัวเอง ไม่มีค่า token
- **provider หลายเจ้า** — ระบบนี้ตั้งใจให้ local เท่านั้น

### 6. คำถามที่ยังไม่มีคำตอบ

1. "ทดสอบการต่อ" ควรลึกแค่ไหน — แค่ `/v1/models` หรือยิง chat จริงหนึ่งครั้ง
   (ยิงจริงแม่นกว่าแต่กินเวลาและโหลดโมเดลอาจต้องรอเป็นนาที)
2. ปิด alias ที่มีคนใช้อยู่ ควรตอบ client ว่าอะไร — 404 เหมือนไม่มี หรือ 503 บอกว่า
   ปิดชั่วคราว
3. ตารางสองชั้นควรยุบ/กางเป็นค่าเริ่มต้นแบบไหน เมื่อส่วนใหญ่มี endpoint เดียว
