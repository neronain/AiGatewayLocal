### 0. ทำไมต้องมีเอกสารนี้

ผู้ใช้ที่ตั้งระบบเองรายงานว่า "งง" กับขั้นตอนสร้างบัญชี — สร้าง user แล้วไง,
workspace คืออะไร, ทำไมสร้าง workspace แล้วไม่มีให้เลือกโมเดล

ไล่โค้ดแล้วพบว่า**โครงไม่ได้ผิด แต่มีของที่ไม่ทำงานปนอยู่** สองอย่าง:

1. `Membership` (ตาราง `enrollments`) — ใส่คนเข้า workspace ได้ แต่**ไม่ถูกอ่าน
   ตอน request เลย** สิ่งที่บังคับใช้จริงคือ `workspace_id` ที่ผูกกับ *key*
   ขั้นตอนที่ดูสำคัญที่สุดจึงไม่มีผลอะไร
2. หน้าตั้งโมเดลของ workspace แสดง checkbox ว่างเสมอ (แก้แล้วใน `a30cdd8`)

ข้อ 2 แก้ไปแล้ว เอกสารนี้ว่าด้วยข้อ 1 — ซึ่งแก้ได้สองทางที่ตรงข้ามกัน และเลือกผิด
แล้วย้อนยาก

### 1. ของที่มีอยู่ตอนนี้ (วัดจากโค้ด ไม่ใช่จากความจำ)

```
User ──< Membership >── Workspace ──< WorkspaceModel
 │                          │
 └────< ApiKey >────────────┘        ApiKey.workspace_id
```

| จุด | บังคับใช้ตอน request | อ่านที่ |
|---|---|---|
| `ApiKey.workspace_id` | **ใช่** | `app/core/auth.py` — จำกัดตาม `WorkspaceModel` |
| `Membership` | **ไม่** | ไม่มีที่ไหนใน `app/core/` หรือ `app/api/openai.py` |
| `User.role` | ใช่ | `is_admin` / `is_manager` |
| `WorkspaceModel` | ใช่ | ไม่มีแถว = ไม่อนุญาต |

`Membership` จึงเป็นบันทึกทางบัญชีอย่างเดียว

### 1.1 LiteLLM ทำยังไง (อ่านจากเอกสาร virtual keys)

key ผูกกับ user หรือ team · รายการโมเดลอยู่ได้ทั้งบน key เองและสืบจากเจ้าของ ·
ไม่ตั้งรายการ = ปฏิเสธ · งบและลิมิตสืบทอดจากเจ้าของเมื่อ key ไม่ได้ตั้งเอง

โครงนี้**เกือบเหมือนของเราแล้ว** ต่างที่ LiteLLM ให้ key ระบุรายการเองได้ด้วย และ
ความเป็นเจ้าของมาจาก user/team ไม่ใช่จากการเลือกตอนออก key

> ข้อจำกัด: อ่านเอกสารหน้าเดียว ไม่ได้อ่านโค้ด LiteLLM · ถ้าจะยึดพฤติกรรมมันเป๊ะ
> ต้องตรวจเพิ่ม

### 2. ตัวเลือก

#### A. ให้ membership มีผล — key สืบสิทธิ์จากกลุ่มของเจ้าของ

ออก key โดยไม่ต้องเลือก workspace · สิทธิ์มาจาก workspace ที่เจ้าของสังกัด

- ✅ ตรงกับที่ผู้ใช้คาดหวังและตรงกับ LiteLLM
- ✅ ย้ายคนข้ามกลุ่มแล้ว key เดิมเปลี่ยนสิทธิ์ตาม ไม่ต้องออกใหม่
- ❌ **เปลี่ยนสิทธิ์ของ key ที่ออกไปแล้ว** — คนที่วันนี้ใช้ได้ทุกโมเดล (key ไม่ผูก
  workspace) พรุ่งนี้อาจถูกจำกัดทันทีที่ถูกใส่เข้ากลุ่ม
- ❌ อยู่หลายกลุ่มแปลว่าอะไร ต้องตัดสิน (union / ต้องเลือกตอนเรียก / ห้ามอยู่หลายกลุ่ม)

#### B. ลบ membership ทิ้ง — เหลือกติกาเดียวคือ key ผูก workspace

- ✅ เล็กที่สุด ชัดที่สุด ไม่มีของหลอกอยู่ในระบบ
- ✅ ไม่กระทบ key ที่ออกไปแล้วเลย
- ❌ ต้องเลือก workspace ทุกครั้งที่ออก key
- ❌ ย้ายคนข้ามกลุ่ม = ต้องออก key ใหม่
- ❌ เสียตารางที่ตอบคำถาม "ใครอยู่วิชาไหน" ซึ่งมหาลัยอยากได้

#### C. ทั้งสองชั้น (แบบ LiteLLM)

key ระบุ workspace เองได้ · ไม่ระบุ = สืบจาก membership ของเจ้าของ

- ✅ ยืดหยุ่นที่สุด
- ❌ กติกาซ้อนกันสองชั้น ซึ่งคือสิ่งที่ทำให้ผู้ใช้งงตั้งแต่แรก

**เลือก A** — ตรงกับความคาดหวัง และ B ทิ้งข้อมูลที่ปลายทางต้องใช้

### 3. ข้อกำหนด — **เลือก A · ทำแล้ว 2026-08-14**

ทั้งหมดอยู่ที่ `permitted_aliases()` ใน `app/core/auth.py` ที่เดียว และใช้ทั้งกับด่านตรวจ
(`assert_model_permitted`) และกับรายการที่โชว์ (`/v1/models`, `/v1/catalog`) · ระหว่างทำ
พบว่าสองอย่างนี้**เคยไม่ตรงกัน**: รายการไม่กรองตาม workspace เลย คนจึงเห็นโมเดลที่ตัวเอง
เรียกไม่ได้ แล้วไปเจอ error ตอนพิมพ์ prompt เสร็จแล้ว — แก้ไปพร้อมกัน

#### FR-40 — สิทธิ์โมเดลมาจากกลุ่มของเจ้าของ key · **P0**

เมื่อ key **ไม่ได้** ผูก workspace ให้ประกอบสิทธิ์จาก workspace ทั้งหมดที่เจ้าของ
สังกัด · เจ้าของไม่อยู่กลุ่มไหนเลย = พฤติกรรมเดิม (ทุกโมเดลที่ role นั้นเห็น)

#### FR-41 — อยู่หลายกลุ่มได้สิทธิ์รวมกัน · **P0**

union ไม่ใช่ intersection · นักศึกษาลงสองวิชาต้องเรียกได้ทั้งสองชุด

#### FR-42 — key ที่ผูก workspace ยังชนะ · **P0**

`ApiKey.workspace_id` ที่ตั้งไว้ยังมีผลเหนือ membership — key ที่ออกให้ระบบเฉพาะ
กิจต้องจำกัดได้โดยไม่ขึ้นกับว่าเจ้าของอยู่กลุ่มไหน

#### FR-43 — ไม่เปลี่ยนสิทธิ์ของ key ที่ออกไปแล้วโดยไม่บอก · **P0**

ข้อนี้สำคัญที่สุด ก่อน deploy ต้องรายงานว่า key ใบไหนจะเปลี่ยนสิทธิ์บ้าง และให้
เลือกได้ว่าจะให้ key เก่าใช้กติกาเดิมต่อ (grandfather) หรือเปลี่ยนตาม

สวิตช์คือ `membership_grants_models` ใน `gateway.yaml` · **default `true`** สำหรับ
ระบบใหม่ เพราะเป็นสิ่งที่ทุกคนเข้าใจว่ามันทำอยู่แล้ว · ระบบที่มี key ใช้งานจริงอยู่ให้ตั้ง
`false` แล้วรัน `scripts/access_change_report.py` ดูก่อนว่าใครกระทบ ค่อยเปิด

#### FR-44 — คอนโซลบอกว่าสิทธิ์มาจากไหน · **P1**

`/v1/catalog` คืน `access: {restricted, reason}` มาด้วย · หน้าเว็บขึ้นบรรทัดว่า
"เห็นเท่านี้เพราะถูกจำกัดโดย …" เหนือรายการโมเดล · ตอนถูกปฏิเสธ error ก็บอกทั้ง
กติกาที่จำกัดและรายการที่เรียกได้จริง แทนที่จะบอกแค่ว่าไม่ได้

#### NFR-40 — ไม่เพิ่ม query ต่อ request · **P0**

**ไม่ผ่านตามตัวอักษร — เพิ่ม 1 query** สำหรับ key ที่ไม่ผูก workspace (เดิม 0 query
เพราะไม่เคยตรวจอะไรเลย) · key ที่ผูก workspace เท่าเดิม

ที่ทำได้คือกันไม่ให้เป็น 2: `_models_via_membership()` join membership กับ
workspace_models ในคำสั่งเดียว ไม่ใช่ถาม "อยู่กลุ่มไหน" แล้วค่อยถาม "กลุ่มนั้นมีอะไร"

วัดจริงบน `/v1/models` (SQLite, 40 ครั้ง): **4 query · median 1.8 ms** ทั้งกรณีที่อยู่ใน
กลุ่มและไม่อยู่ — ก่อนรวม query เป็น 5 query / 1.99 ms ตอนอยู่ในกลุ่ม

ถ้าวันหนึ่งมันสำคัญขึ้นมา ทางลดคือย้ายไปทำตอน authenticate ซึ่ง query key กับ user
อยู่แล้ว หรือ cache ตาม `api_key_id` อายุสั้น ๆ · ยังไม่ทำเพราะยังไม่มีหลักฐานว่าคุ้ม

### 5.5 ผลการทดลองติดตั้ง LiteLLM จริง (2026-08-14)

คำถามคือ "ติดตั้ง LiteLLM แล้วเขียนส่วนของเราเพิ่ม" แทนการเขียนเองทั้งหมด ได้ไหม
ตอบด้วยการติดตั้งจริงแล้วยิงใส่ backend ของเราเอง ไม่ใช่จากเอกสาร

รอบแรกติดตั้งด้วย pip · รอบสองด้วย image ทางการ `ghcr.io/berriai/litellm:main-stable`
(litellm 1.96.2 · fastapi 0.136.3) ยิงชุดเดิมทั้งหมดกับ muse-glimmer (llama.cpp,
spark-head) และ qwen3-coder-next (vLLM, msi-6)

**ผลรอบสอง: ผ่าน 8/8**

| | ผล |
|---|---|
| `/v1/chat/completions` | ผ่าน |
| `/v1/messages` (ไม่สตรีม) | ผ่าน — `type=message` |
| `tool_use` | ผ่าน — `read_file{'path': 'config.yaml'}` |
| `tool_result` round trip | ผ่าน — `end_turn` |
| vision (PNG 224×224) | ผ่าน — ตอบ `red` |
| system prompt 21,840 ตัวอักษร + tools | ผ่าน — `stop=tool_use` |
| สตรีม `/v1/messages` · coder-next | ผ่าน — 5 delta |
| สตรีม `/v1/messages` · muse (reasoning) | **ผ่าน** — 5 delta ตรงกับที่ llama.cpp ส่ง |

#### แก้ข้อสรุปรอบแรก: LiteLLM ไม่ได้พัง — probe ของเราเองผิด

รอบแรกบันทึกไว้ว่า "reasoning model สตรีมแล้วได้ 0 delta ข้อความว่าง" และสรุปว่า
**เป็นข้อบกพร่องของ LiteLLM ในกรณีใช้งานหลักของเรา** ข้อสรุปนั้น**ผิด**

ตัวแปรจริงคือ `max_tokens` ไม่ใช่ LiteLLM · โมเดล reasoning ใช้ token ไปกับการคิด
ก่อน ถ้างบไม่พอก็หมดตั้งแต่ยังไม่ทันตอบ กวาดค่าดูได้ชัด:

| `max_tokens` | 32 | 64 | 128 | 256 | 512 |
|---|---|---|---|---|---|
| muse (reasoning) | 0 | 0 | 0 | **5** | **5** |
| coder-next (ไม่ใช่ reasoning) | 5 | 5 | 5 | 5 | 5 |

รอบแรกยิงด้วยงบต่ำ จึงวัด "โมเดลคิดจนหมดโควตา" แล้วอ่านเป็น "LiteLLM แปลสตรีมพัง"
เป็นกับดักตัวเดียวกับที่ทำให้ `max_tokens=32` ให้ผลลวงมาก่อนหน้านี้ใน session เดียวกัน

#### ที่ต่างกันจริงระหว่างสองตัว: เนื้อหาการคิด

ยิงคำถามเดียวกัน งบ 64 token:

| | เหตุการณ์ที่ client ได้รับ |
|---|---|
| LiteLLM | เปิด `content_block_start[thinking]` ว่างเปล่าแล้วปิด · ไม่มีอะไรอีก |
| ของเรา | `thinking_delta` 61 ครั้ง + `signature_delta` 1 ครั้ง — รูปแบบ extended thinking ตามสเปก |

ของเราส่งการคิดออกไปตามสเปก LiteLLM ทิ้ง · ทั้งคู่ให้ข้อความสุดท้ายว่างเท่ากันเมื่องบ
ไม่พอ ต่างกันที่ฝั่งเราผู้ใช้เห็นว่าโมเดลกำลังทำงานอยู่ ไม่ใช่เงียบสนิท

> **บทเรียนเชิงปฏิบัติ** โมเดล reasoning ต้องการ `max_tokens` มากกว่าที่คิด — งบต่ำ
> ให้ `stop_reason=end_turn` พร้อมข้อความว่าง ซึ่งดูเหมือนระบบพังทั้งที่โมเดลแค่คิดจน
> หมดโควตา ตั้งอย่างน้อย 256 สำหรับ muse

#### ความยากตอนติดตั้ง — image ทางการแก้ให้หมดแล้ว

| ปัญหาตอน pip | image ทางการ |
|---|---|
| `pip install litellm[proxy]` ได้ FastAPI 0.141 ซึ่ง proxy ใช้ไม่ได้ (`get_flat_dependant`) | ไม่เจอ — มาพร้อม fastapi 0.136.3 |
| `litellm` CLI พัง (`No module named proxy_server`) | ไม่เจอ — `--config` ทำงานปกติ |

**ถ้าจะประเมิน LiteLLM ให้ใช้ image ทางการเท่านั้น** ปัญหาสองข้อบนเป็นของวิธีติดตั้ง
ล้วน ๆ และการเอาไปตัดสินตัว LiteLLM เองคือการวัดผิดที่

#### สรุปการตัดสินใจ

ตัวขวางที่บันทึกไว้รอบแรกไม่มีอยู่จริง · LiteLLM ใช้กับ backend ของเราได้ครบทุกข้อ
ที่ทดสอบ แต่**ยังไม่ย้าย** ด้วยเหตุผลที่เหลืออยู่:

- ความสามารถของโมเดลใน LiteLLM มาจากตารางค่าคงที่ — `/model_group/info` รายงาน
  `supports_vision: false` ให้ muse ทั้งที่ทดสอบแล้วว่าอ่านภาพได้ · ของเราวัดจริงแล้ว
  บันทึกพร้อมเวลาที่วัด (FR-53) ซึ่งเป็นหลักการที่ทั้งระบบยืนอยู่บนมัน
- ของที่เคยเป็นเหตุผลให้ย้าย (virtual key, รายการโมเดลต่อ key, ขอบเขตตามกลุ่ม) ทำเสร็จ
  ไปแล้วใน v1.4/v1.5 นี้ พร้อม failover ที่ LiteLLM ไม่มีให้ในระดับเดียวกัน
- การคิดของโมเดลถูกส่งต่อตามสเปก ไม่ถูกทิ้ง

ทางที่ยังเปิดอยู่: ใช้ LiteLLM เป็นชั้นบริหารจัดการภายนอก (budget, spend tracking
ข้าม provider) แล้วให้คำขอวิ่งผ่านทางของเรา — ประเมินได้เมื่อมีคนขอ ไม่ใช่ตอนนี้

### 6. สิ่งที่ **ไม่** ทำในรอบนี้

- ไม่รื้อไปเป็น LiteLLM · ถ้าต้องการพฤติกรรม LiteLLM ครบ **ใช้ LiteLLM ตรง ๆ
  คุ้มกว่า** — 100+ provider, spend tracking พร้อม pricing, load balancing,
  caching ซึ่งเขียนตามให้ครบคือหลายเดือน
- ไม่เพิ่ม organization ซ้อนบน workspace จนกว่าจะมีคนขอ
- ไม่ทำ budget เป็นเงิน — ระบบนี้รันโมเดลบนเครื่องตัวเอง ไม่มีค่า token
- ไม่แตะ quota, routing, capability registry, model test suite

### 7. คำถามที่ยังไม่มีคำตอบ

**1. นักศึกษาที่จบเทอมแล้วแต่ยังอยู่ในกลุ่ม — หมดอายุอัตโนมัติตาม `Workspace.term` ไหม**

*เสนอ: ไม่* · ให้ `term` เป็นป้ายบอกข้อมูลอย่างเดียวเหมือนตอนนี้ แล้วให้ key หมดอายุ
ด้วย `expires_at` ซึ่งมีอยู่แล้วและผู้ออก key เห็นตอนกดออก · การหมดอายุที่ผูกกับเทอม
จะทำงานเงียบ ๆ ในวันที่ไม่มีใครดูอยู่ แล้วคนทั้งห้องเรียกไม่ได้พร้อมกันโดยไม่มีใคร
กดอะไรเลย — เป็นความล้มเหลวแบบที่หาสาเหตุยากที่สุด · ถ้าอยากได้จริงควรเป็น
*รายงาน* ว่า "กลุ่มนี้จบเทอมแล้ว มีสมาชิก N คน" ให้คนตัดสินใจ ไม่ใช่ตัดเอง

**2. `manager` ควรถูกจำกัดตามกลุ่มด้วยไหม หรือข้ามเหมือนตอนนี้**

**ตอบแล้ว (เจ้าของระบบ · 2026-08-14): จำกัด — ตามกลุ่มที่เขาดูแล**

`manager` จึงถูกคิดสิทธิ์แบบเดียวกับ member ทุกประการ · คนที่ดูแล CS101 ไม่มีเหตุผล
ที่จะแจกโมเดลของ ART200 ได้ · ส่วน `admin` **ไม่ถูกจำกัด** เพราะเป็นคนดูแล gateway
ทั้งตัว ถ้าบังคับให้จำกัดด้วยก็ต้องใส่ admin เข้าทุก workspace ซึ่งเป็นงานประจำที่ไม่มี
วันจบและไม่ได้เพิ่มความปลอดภัยอะไร

**2ก. แล้วฝั่งงานผู้ดูแลล่ะ · ตอบแล้ว: จำกัดด้วย (2026-08-14)**

ทั้ง 13 เส้นทางที่ manager เข้าถึงได้ถูกจำกัดตาม workspace ที่ตัวเองสังกัด:

| เส้นทาง | ขอบเขต |
|---|---|
| `GET /admin/users` | เฉพาะคนในกลุ่มตัวเอง (+ ตัวเองเสมอ) |
| `GET /admin/workspaces` | เฉพาะกลุ่มตัวเอง |
| `POST .../{id}/models` | เฉพาะกลุ่มตัวเอง **และเฉพาะโมเดลที่ตัวเองใช้ได้** |
| `POST .../{id}/join`, `DELETE .../members/{id}` | เฉพาะกลุ่มตัวเอง |
| `POST /admin/api-keys` | ออกให้คนในกลุ่มตัวเอง · workspace ต้องเป็นของตัวเอง · โมเดลต้องอยู่ในสิทธิ์ตัวเอง |
| `GET`/`DELETE /admin/api-keys` | เฉพาะ key ของคนในกลุ่มตัวเอง |
| `GET /admin/quota-policies` | global + ของกลุ่มตัวเอง + ของตัวเอง |
| `GET /admin/models/{alias}/compatibility`, `/test-runs/{id}` | เฉพาะ alias ที่ตัวเองใช้ได้ |
| `GET /admin/usage/*` | เฉพาะคนในกลุ่มตัวเอง |

ข้อที่สำคัญที่สุดคือ **"ห้ามแจกสิ่งที่ตัวเองไม่มี"** — ถ้าไม่มีข้อนี้ การจำกัดสิทธิ์โมเดล
เป็นแค่ฉากหน้า เพราะ manager เปิดโมเดลใด ๆ ให้กลุ่มที่ตัวเองอยู่ ก็เท่ากับให้ตัวเอง

**ค่า default กลับทางกับสิทธิ์เรียกโมเดล และตั้งใจ**: manager ที่ยังไม่อยู่กลุ่มไหน
**ดูแลอะไรไม่ได้เลย** ส่วน member ที่ไม่อยู่กลุ่มไหน**ใช้ได้ทุกอย่าง** เหตุผลคนละเรื่อง
กัน — ฝั่งโมเดลเปิดไว้เพื่อไม่ให้ระบบที่ยังไม่ใช้ workspace พังยกชุด ส่วนฝั่งผู้ดูแล
ไม่มีประวัติแบบนั้น และถ้าเปิดไว้ การเลื่อนใครเป็น manager จะเท่ากับยกทั้งสถาบันให้
เงียบ ๆ · API บอกเหตุผลเป็นประโยคด้วย ไม่ใช่คืนรายการว่างเฉย ๆ

การปฏิเสธ key ของกลุ่มอื่นตอบว่า "not found" เหมือน id ที่ไม่มีจริง — endpoint นี้
ไม่ควรใช้ไล่เดาว่าในระบบมี key อะไรอยู่บ้าง

**3. อยู่หลายกลุ่มที่ตั้งโมเดลขัดกัน — union พอไหม หรือต้องมีทาง deny ทับ**

*เสนอ: union พอ ไม่ต้องมี deny* · deny ที่ทับ allow ได้แปลว่าการใส่คนเข้ากลุ่มเพิ่ม
ทำให้เขา **เสีย** สิทธิ์ ซึ่งตรงข้ามกับสิ่งที่ทุกคนคาดจากคำว่า "เพิ่มเข้ากลุ่ม" และเป็น
ความเสี่ยงที่ §5 ระบุไว้เองแล้ว · ถ้าต้องห้ามโมเดลไหนจริง ๆ ให้ห้ามที่ตัวโมเดล
(`visibility` หรือปิดมันไปเลยด้วย FR-51) ซึ่งเป็นที่เดียวและอ่านออกว่าใครห้าม
ไม่ใช่ผลลัพธ์ของการอยู่หลายกลุ่มพร้อมกัน
