### 0. ทำไมต้องมีเอกสารนี้

ผู้ใช้ที่ตั้งระบบเองรายงานว่า "งง" กับขั้นตอนสร้างบัญชี — สร้าง user แล้วไง,
workspace คืออะไร, ทำไมสร้าง workspace แล้วไม่มีให้เลือกโมเดล

ไล่โค้ดแล้วพบว่า**โครงไม่ได้ผิด แต่มีของที่ไม่ทำงานปนอยู่** สองอย่าง:

1. `Membership` (ตาราง `enrollments`) — ใส่คนเข้า workspace ได้ แต่**ไม่ถูกอ่าน
   ตอน request เลย** สิ่งที่บังคับใช้จริงคือ `workspace_id` ที่ผูกกับ *key*
   ขั้นตอนที่ดูสำคัญที่สุดจึงไม่มีผลอะไร
2. หน้าตั้งโมเดลของ workspace แสดง checkbox ว่างเสมอ (แก้แล้วใน `a30cdd8`)

ข้อ 2 แก้ไปแล้ว เอกสารนี้ว่าด้วยข้อ 1 — ซึ่งแก้ได้สองทางที่ตรงข้ามกัน และเลือกผิด
แล้วย้อนยาก

### 1. ของที่มีอยู่ตอนนี้ (วัดจากโค้ด ไม่ใช่จากความจำ)

```
User ──< Membership >── Workspace ──< WorkspaceModel
 │                          │
 └────< ApiKey >────────────┘        ApiKey.workspace_id
```

| จุด | บังคับใช้ตอน request | อ่านที่ |
|---|---|---|
| `ApiKey.workspace_id` | **ใช่** | `app/core/auth.py` — จำกัดตาม `WorkspaceModel` |
| `Membership` | **ไม่** | ไม่มีที่ไหนใน `app/core/` หรือ `app/api/openai.py` |
| `User.role` | ใช่ | `is_admin` / `is_manager` |
| `WorkspaceModel` | ใช่ | ไม่มีแถว = ไม่อนุญาต |

`Membership` จึงเป็นบันทึกทางบัญชีอย่างเดียว

### 1.1 LiteLLM ทำยังไง (อ่านจากเอกสาร virtual keys)

key ผูกกับ user หรือ team · รายการโมเดลอยู่ได้ทั้งบน key เองและสืบจากเจ้าของ ·
ไม่ตั้งรายการ = ปฏิเสธ · งบและลิมิตสืบทอดจากเจ้าของเมื่อ key ไม่ได้ตั้งเอง

โครงนี้**เกือบเหมือนของเราแล้ว** ต่างที่ LiteLLM ให้ key ระบุรายการเองได้ด้วย และ
ความเป็นเจ้าของมาจาก user/team ไม่ใช่จากการเลือกตอนออก key

> ข้อจำกัด: อ่านเอกสารหน้าเดียว ไม่ได้อ่านโค้ด LiteLLM · ถ้าจะยึดพฤติกรรมมันเป๊ะ
> ต้องตรวจเพิ่ม

### 2. ตัวเลือก

#### A. ให้ membership มีผล — key สืบสิทธิ์จากกลุ่มของเจ้าของ

ออก key โดยไม่ต้องเลือก workspace · สิทธิ์มาจาก workspace ที่เจ้าของสังกัด

- ✅ ตรงกับที่ผู้ใช้คาดหวังและตรงกับ LiteLLM
- ✅ ย้ายคนข้ามกลุ่มแล้ว key เดิมเปลี่ยนสิทธิ์ตาม ไม่ต้องออกใหม่
- ❌ **เปลี่ยนสิทธิ์ของ key ที่ออกไปแล้ว** — คนที่วันนี้ใช้ได้ทุกโมเดล (key ไม่ผูก
  workspace) พรุ่งนี้อาจถูกจำกัดทันทีที่ถูกใส่เข้ากลุ่ม
- ❌ อยู่หลายกลุ่มแปลว่าอะไร ต้องตัดสิน (union / ต้องเลือกตอนเรียก / ห้ามอยู่หลายกลุ่ม)

#### B. ลบ membership ทิ้ง — เหลือกติกาเดียวคือ key ผูก workspace

- ✅ เล็กที่สุด ชัดที่สุด ไม่มีของหลอกอยู่ในระบบ
- ✅ ไม่กระทบ key ที่ออกไปแล้วเลย
- ❌ ต้องเลือก workspace ทุกครั้งที่ออก key
- ❌ ย้ายคนข้ามกลุ่ม = ต้องออก key ใหม่
- ❌ เสียตารางที่ตอบคำถาม "ใครอยู่วิชาไหน" ซึ่งมหาลัยอยากได้

#### C. ทั้งสองชั้น (แบบ LiteLLM)

key ระบุ workspace เองได้ · ไม่ระบุ = สืบจาก membership ของเจ้าของ

- ✅ ยืดหยุ่นที่สุด
- ❌ กติกาซ้อนกันสองชั้น ซึ่งคือสิ่งที่ทำให้ผู้ใช้งงตั้งแต่แรก

**เสนอ: A** — ตรงกับความคาดหวัง และ B ทิ้งข้อมูลที่ปลายทางต้องใช้

### 3. ข้อกำหนด (ถ้าเลือก A)

#### FR-40 — สิทธิ์โมเดลมาจากกลุ่มของเจ้าของ key · **P0**

เมื่อ key **ไม่ได้** ผูก workspace ให้ประกอบสิทธิ์จาก workspace ทั้งหมดที่เจ้าของ
สังกัด · เจ้าของไม่อยู่กลุ่มไหนเลย = พฤติกรรมเดิม (ทุกโมเดลที่ role นั้นเห็น)

#### FR-41 — อยู่หลายกลุ่มได้สิทธิ์รวมกัน · **P0**

union ไม่ใช่ intersection · นักศึกษาลงสองวิชาต้องเรียกได้ทั้งสองชุด

#### FR-42 — key ที่ผูก workspace ยังชนะ · **P0**

`ApiKey.workspace_id` ที่ตั้งไว้ยังมีผลเหนือ membership — key ที่ออกให้ระบบเฉพาะ
กิจต้องจำกัดได้โดยไม่ขึ้นกับว่าเจ้าของอยู่กลุ่มไหน

#### FR-43 — ไม่เปลี่ยนสิทธิ์ของ key ที่ออกไปแล้วโดยไม่บอก · **P0**

ข้อนี้สำคัญที่สุด ก่อน deploy ต้องรายงานว่า key ใบไหนจะเปลี่ยนสิทธิ์บ้าง และให้
เลือกได้ว่าจะให้ key เก่าใช้กติกาเดิมต่อ (grandfather) หรือเปลี่ยนตาม

#### FR-44 — คอนโซลบอกว่าสิทธิ์มาจากไหน · **P1**

แต่ละ key ต้องแสดงว่าโมเดลที่เรียกได้มาจาก workspace ที่ผูกไว้ หรือมาจากกลุ่มของ
เจ้าของ และมาจากกลุ่มไหนบ้าง

#### NFR-40 — ไม่เพิ่ม query ต่อ request · **P0**

ทุกวันนี้ตรวจสิทธิ์ด้วย query เดียว · ประกอบจากหลายกลุ่มต้องไม่กลายเป็น N+1 ·
วัดก่อน/หลังด้วย `litegate_request_duration_seconds`

ตรรกะเองมีเทสคุมไว้ที่ `tests/test_access_change_report.py` — คนที่อยู่ CS101

intersection · key ที่ผูก workspace ไว้แล้วไม่สนใจกลุ่มของเจ้าของ · key ที่ถูก
เพิกถอนไม่ถูกนับ (ไม่งั้นตัวเลขดูน่ากลัวเกินจริง)

### 5.5 ผลการทดลองติดตั้ง LiteLLM จริง (2026-08-14)

คำถามคือ "ติดตั้ง LiteLLM แล้วเขียนส่วนของเราเพิ่ม" แทนการเขียนเองทั้งหมด ได้ไหม
ตอบด้วยการติดตั้งจริงแล้วยิงใส่ backend ของเราเอง ไม่ใช่จากเอกสาร

**ที่ใช้ได้ — ทดสอบกับ muse-glimmer (llama.cpp, spark-head) และ qwen3-coder-next
(vLLM, msi-6) ผ่าน LiteLLM ที่ชี้ไป `api_base` ของทั้งสอง**

| | ผล |
|---|---|
| `/v1/chat/completions` | ผ่าน |
| `/v1/messages` (ไม่สตรีม) | ผ่าน — `type=message` |
| `tool_use` | ผ่าน — `read_file{'path': 'config.yaml'}` |
| `tool_result` round trip | ผ่าน — `end_turn` ตอบถูก |
| vision (PNG 224×224) | ผ่าน — ตอบ `red` |
| system prompt 21,840 ตัวอักษร + tools | ผ่าน — เรียก tool ได้ |

**ที่ใช้ไม่ได้ — และตรงกับโมเดลที่เรารันอยู่พอดี**

| โมเดล | `content_block_delta` | ข้อความที่ client ได้รับ |
|---|---|---|
| `coder-next` (ไม่ใช่ reasoning) | 5 | `'1 \\n2 \\n3'` |
| `muse` (reasoning) | **0** | **`''`** |
| `muse` ยิงตรงที่ llama.cpp | 58 | ครบ |

LiteLLM เปิด `content_block_start` ชนิด `thinking` ที่ว่างเปล่าแล้วปิดทันที
**คำตอบไม่ถูกส่งออกมาเลย** ไม่ใช่แค่ไม่สตรีมทีละ token

Claude Code สตรีมเสมอ และโมเดลหลักที่เรารัน (Muse-Glimmer, gpt-oss-120b) เป็น
reasoning model ทั้งคู่ — นี่จึงไม่ใช่ข้อบกพร่องเล็กน้อย แต่คือกรณีใช้งานหลัก

**ความยากตอนติดตั้ง (บันทึกไว้เพราะเป็นต้นทุนจริง)**

- `pip install litellm[proxy]` วันนี้ได้ FastAPI 0.141 ซึ่ง proxy ใช้ไม่ได้
  (`ImportError: cannot import name 'get_flat_dependant'`) ต้อง pin `fastapi<0.116`
- `litellm` CLI พัง (`ModuleNotFoundError: No module named 'proxy_server'`)
  ทั้งบน Python 3.12 และ 3.14 — ต้องรันผ่าน `uvicorn litellm.proxy.proxy_server:app`
- ยังไม่ได้ทดสอบ image ทางการ (`ghcr.io/berriai/litellm`) ซึ่งน่าจะ pin ไว้ครบแล้ว
  — **ควรลองก่อนตัดสินใจขั้นสุดท้าย** เพราะสองข้อบนอาจหายไปเลย

**สิ่งที่ผลนี้บอก**

โครงสิทธิ์ของ LiteLLM (key → team → models) ใกล้กับที่ §2 ตัวเลือก A เสนอมาก และ
ถ้าย้ายไปจริงจะได้ virtual key, budget, spend tracking มาฟรี แต่ต้องแก้เรื่อง
streaming ของ reasoning model ก่อน — ไม่งั้นแลกฟีเจอร์บริหารจัดการมาด้วยการเสีย
กรณีใช้งานหลักไป

ทางที่ยังเปิดอยู่และยังไม่ได้ประเมิน: ใช้ LiteLLM เป็นชั้นบริหารจัดการ (key/team/
budget) แล้วให้คำขอที่ต้องสตรีมวิ่งผ่านทางของเราเอง — ได้ทั้งสองอย่างโดยไม่ต้องรอ
ให้ upstream แก้

### 6. สิ่งที่ **ไม่** ทำในรอบนี้

- ไม่รื้อไปเป็น LiteLLM · ถ้าต้องการพฤติกรรม LiteLLM ครบ **ใช้ LiteLLM ตรง ๆ
  คุ้มกว่า** — 100+ provider, spend tracking พร้อม pricing, load balancing,
  caching ซึ่งเขียนตามให้ครบคือหลายเดือน
- ไม่เพิ่ม organization ซ้อนบน workspace จนกว่าจะมีคนขอ
- ไม่ทำ budget เป็นเงิน — ระบบนี้รันโมเดลบนเครื่องตัวเอง ไม่มีค่า token
- ไม่แตะ quota, routing, capability registry, model test suite

### 7. คำถามที่ยังไม่มีคำตอบ

**1. นักศึกษาที่จบเทอมแล้วแต่ยังอยู่ในกลุ่ม — หมดอายุอัตโนมัติตาม `Workspace.term` ไหม**

*เสนอ: ไม่* · ให้ `term` เป็นป้ายบอกข้อมูลอย่างเดียวเหมือนตอนนี้ แล้วให้ key หมดอายุ
ด้วย `expires_at` ซึ่งมีอยู่แล้วและผู้ออก key เห็นตอนกดออก · การหมดอายุที่ผูกกับเทอม
จะทำงานเงียบ ๆ ในวันที่ไม่มีใครดูอยู่ แล้วคนทั้งห้องเรียกไม่ได้พร้อมกันโดยไม่มีใคร
กดอะไรเลย — เป็นความล้มเหลวแบบที่หาสาเหตุยากที่สุด · ถ้าอยากได้จริงควรเป็น
*รายงาน* ว่า "กลุ่มนี้จบเทอมแล้ว มีสมาชิก N คน" ให้คนตัดสินใจ ไม่ใช่ตัดเอง

**2. `manager` ควรถูกจำกัดตามกลุ่มด้วยไหม หรือข้ามเหมือนตอนนี้** ← *ต้องให้เจ้าของระบบตอบ*

ตอบไม่ได้จากโค้ด เพราะขึ้นกับว่า `manager` ในมหาลัยหมายถึงใคร:

* ถ้าหมายถึง **อาจารย์ประจำวิชา** — ควรถูกจำกัดตามกลุ่มที่ตัวเองสอน ไม่งั้นอาจารย์
  วิชาหนึ่งออก key ให้ใช้โมเดลของอีกวิชาได้
* ถ้าหมายถึง **เจ้าหน้าที่ไอทีของคณะ** — ต้องข้ามได้ ไม่งั้นต้องใส่เข้าทุกกลุ่มในคณะ
  ซึ่งกลายเป็นงานประจำที่ไม่มีวันจบ

กระทบ FR-40 โดยตรงและกระทบว่า `permitted_aliases()` ต้องรู้จัก role หรือไม่ · **ต้อง
ตอบก่อนเริ่มงาน 3** ไม่งั้นเขียนไปแล้วต้องรื้อ

**3. อยู่หลายกลุ่มที่ตั้งโมเดลขัดกัน — union พอไหม หรือต้องมีทาง deny ทับ**

*เสนอ: union พอ ไม่ต้องมี deny* · deny ที่ทับ allow ได้แปลว่าการใส่คนเข้ากลุ่มเพิ่ม
ทำให้เขา **เสีย** สิทธิ์ ซึ่งตรงข้ามกับสิ่งที่ทุกคนคาดจากคำว่า "เพิ่มเข้ากลุ่ม" และเป็น
ความเสี่ยงที่ §5 ระบุไว้เองแล้ว · ถ้าต้องห้ามโมเดลไหนจริง ๆ ให้ห้ามที่ตัวโมเดล
(`visibility` หรือปิดมันไปเลยด้วย FR-51) ซึ่งเป็นที่เดียวและอ่านออกว่าใครห้าม
ไม่ใช่ผลลัพธ์ของการอยู่หลายกลุ่มพร้อมกัน
